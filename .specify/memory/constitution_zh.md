# PowerX 宪法

## 核心原则

### I. 插件优先架构

PowerX 的所有业务域都以 **插件（Plugin）** 的形式存在。  
插件必须独立、可测试、可版本化，不得在内核中放置业务逻辑。  
每个插件通过 `provides` / `consumes` 声明自身能力，仅通过官方契约（gRPC、事件总线、SDK）交互。

### II. 规范驱动开发

所有开发从 `spec.md` 开始，而非代码。  
每个功能遵循完整的 Spec-Kit 生命周期：  
`/specify → /clarify → /plan → /tasks → /implement → /analyze`。  
每个功能目录 `specs/<domain>/<feature>/` 必须包含 **三件套**：  
`spec.md`、`plan.md`、`tasks.md`。  
未通过规范审批，不得进入实现阶段。

### III. 多租户与安全优先

PowerX 面向多租户安全架构设计。  
所有 API、存储、缓存与消息系统均需传递租户上下文。  
RBAC 权限与审计日志为强制项。  
每个插件运行在最小权限沙箱内，隔离访问。

### IV. 智能体与工作流集成

PowerX 内置 Agent 运行时与工作流引擎。  
所有工作流均以 YAML/Spec 定义，所有智能体操作均可追溯。  
智能体可调用插件，但不得修改其数据库或二进制文件。  
所有 Agent/MCP 执行命令必须遵循本宪法。

### V. 可观测性与质量门禁

每个服务与插件必须具备：

- 结构化 JSON 日志（含 `trace_id` 与 `tenant_id`）
- 指标（`qps`、`error_rate`、`p95_latency`）
- OpenTelemetry Trace  
- ≥80% 测试覆盖率与性能基线  
未通过质量门禁，不得合并或发布。

---

## 附加约束

### 安全与合规

- 认证：JWT/OIDC（RS256/JWKS），禁止对称密钥。  
- 授权：统一 RBAC 模型（`<domain.action>`）。  
- 数据保护：静态与传输均加密。  
- 依赖扫描：每周执行一次；高危漏洞24小时内修复。

### 性能标准

- API p95 延迟 <200ms  
- 插件启动时间 <5s  
- 内存占用 <256MB（超限需说明）  
- 数据迁移必须提供 `up` 与 `down` 脚本。

## 开发流程

1. **规范优先**：从 `/specify` 开始  
2. **澄清阶段**：通过 `/clarify` 解决不确定项  
3. **规划与宪法检查**：`/plan` 验证设计是否符合宪法  
4. **任务生成**：`/tasks` 生成基于TDD的任务清单  
5. **实现阶段**：`/implement` 按测试优先原则执行  
6. **分析复查**：`/analyze` 校验一致性与覆盖率  

代码评审必须核对：

- 规范三件套是否完整  
- RBAC、审计、租户隔离是否落实  
- 指标与追踪是否接入  
- 是否通过宪法合规检查

---

## 治理机制

本宪法高于其他规范。  
修订需：

- 提交 RFC，说明动机、影响与迁移方案  
- 经 **PowerX 技术委员会** 审批  
- 更新版本并通过 Spec-Kit 同步公告  
所有 PR 必须验证宪法合规性，并说明复杂度合理性。
