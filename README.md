# PowerX – 下一代插件化业务引擎

## 🎯 核心理念

PowerX 的目标是成为一个 **模块化、可扩展、可插拔的业务操作系统**。
它不仅仅是一个 CRM / 电商 / SCRM 应用，而是一个能让这些系统 **以插件形式共存并协作** 的底座。

一句话：**PowerX = 业务内核 + 插件市场 + 多端前后端统一协议**。

---

## 🏗️ 架构哲学

PowerX 遵循三个核心原则：

1. **内核最小化**

  * 内核只提供通用能力：用户与组织（IAM）、权限与访问控制（RBAC）、事件总线（Event Bus）、审计（Audit）、数据库抽象（DB Layer）、运行时流引擎（Flow）。
  * 这些能力作为 SDK (`pkg/corex/*`) 暴露，任何插件和外部系统都可以复用。

2. **插件优先**

  * 业务功能（电商、SCRM、审批流、直播…）一律作为插件。
  * 插件通过 **契约（Contract）** 与内核对接，独立开发、独立部署、独立数据库 Schema。
  * 插件可由官方/第三方/客户自己开发，并通过 **插件市场** 分发。

3. **契约驱动**

  * 插件之间 **不直接依赖**，通过 **契约接口 / 事件订阅** 解耦。
  * 所有对外接口（HTTP/gRPC）、事件（Event Topics）、数据模型（OpenAPI/Proto）均在 `/contracts` 目录集中管理。
  * 内置工具链会自动生成 SDK（Go/TypeScript），保证前后端一致。

---

## 🔑 核心组件

* **IAM（身份与组织）**

  * 用户、部门、角色、标签
  * 所有插件共享的组织架构

* **RBAC（权限控制）**

  * 统一权限模型（Role/Policy）
  * 可扩展至插件级别：插件只声明“资源与动作”，授权由内核托管

* **Event Bus（事件总线）**

  * 插件间的主要通信机制
  * 支持 Local/Redis 实现
  * 插件只需订阅 Topic，不关心消息来源

* **Audit（审计日志）**

  * 统一采集所有事件/操作
  * 内核级别可扩展至合规（安全/风控）

* **DB Layer（数据库抽象）**

  * 多租户隔离（Tenant）
  * 插件独立 Schema，但共享 Postgres/MySQL 实例
  * 统一迁移工具（Goose 兼容）

* **Flow（业务流程引擎）**

  * 内置可编排的执行流（Plan/Task/Node）
  * 插件可挂载定制 Flow 节点

## 🔌 插件机制

* 插件包：一个独立目录（或 zip 包），包含 `plugin.yaml`、后端可执行文件、前端资源。
* 插件安装：丢进 `/plugins` 目录即可，系统启动时扫描注册。
* 插件前端：自动挂载到 Admin 菜单（`/api/v1/admin/manifest` 提供动态菜单）。
* 插件通信：通过事件总线或契约接口，而非直接调用。

---

## 🖥️ 多端支持

PowerX 内置四类前端壳：

* **Admin 管理后台**：动态加载菜单和插件页面，适合运营/管理人员。
* **Web User 前端**：C 端用户界面。
* **MiniApp 小程序**：轻量级触达场景。
* **OpenAPI**：第三方系统通过统一 API 调用。

所有前端共享 **统一契约**，SDK 自动生成，避免重复造轮子。

---

## 🔄 与传统系统的区别

* **不是一个大而全的单体应用**，而是一个「业务内核 + 插件市场」。
* **比微服务更轻**：不用每个模块独立部署，而是统一宿主+插件子进程。
* **比 SaaS 更自由**：企业可选择安装哪些插件，甚至自研插件。
* **开发体验更友好**：提供 Go/TS SDK，第三方只需关心契约，而非宿主内部。

## 🚀 典型场景

* 内置 CRM + 电商 + SCRM = 快速搭建企业数字化平台。
* 客户需要审批流？→ 安装官方插件。
* 客户需要直播？→ 第三方公司开发插件，上传到市场。
* 企业自己有定制逻辑？→ fork 插件 SDK，写个自研插件接上去。

---

## 🛠️ 面向对象（Persona）

* **企业 CTO**：用 PowerX 作为数字化操作系统，按需安装插件，减少定制化成本。
* **第三方开发商**：通过插件市场发布行业插件，复用 PowerX 内核能力。
* **开发团队**：统一 SDK + 契约驱动开发，前后端一致，不用重复维护 DTO。
* **运维人员**：插件可控、隔离，简单安装/升级，不影响核心系统。
