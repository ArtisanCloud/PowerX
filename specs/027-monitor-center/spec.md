# Feature Specification: 监控中心闭环（Backup + Logs）

**Feature Branch**: `027-monitor-center`  
**Created**: 2026-04-10  
**Updated**: 2026-10-29

**Status**: In Progress（US8 本地整站恢复、切换和中断补偿已实现；Linux／生产插件／真实定时跨环境验收待完成；US9 首批只读切片已本地实现，完整治理与部署验收待完成）
**Input**: User description: "先做自动备份功能，在监控中心形成可观察闭环；再补齐日志监控方案（loki/file/stdio）"

**Domain Ownership**: CoreX (`corex.ops`)  
**Transport Exemption (This Iteration)**: 本期仅交付 Admin HTTP 闭环能力；gRPC 合同与实现延期到后续里程碑（需在后续 spec/plan/tasks 中显式补齐）。

## Clarifications

### Session 2026-04-10（Backup）

- Q: 自动备份的执行频率基线要定成哪种？ → A: B（每 6 小时一次）
- Q: 自动备份产物的保留策略，默认保留多少份？ → A: B（保留最近 14 份）
- Q: 恢复演练的默认执行节奏要定成哪种？ → A: A（每周一次）
- Q: 备份失败后的告警升级规则，默认采用哪种？ → A: B（连续 2 次失败升级为高优先级告警）
- Q: 定时备份任务的执行时区默认采用哪种？ → A: B（固定 Asia/Shanghai）

### Session 2026-04-13（Logs）

- Q: 监控日志页是否只支持 Loki？ → A: 否，必须支持 `loki/file/stdio` 三驱动，并按能力降级。
- Q: 正式环境日志检索链路怎么定？ → A: 采用“应用内查询 + Grafana 深链”双层模式。
- Q: file/stdio 驱动是否复用 Loki 全功能？ → A: 否，必须明确能力矩阵并在 UI 显示限制。

### Session 2026-04-24（Plugin Logger 对齐）

- Q: 是否需要在 027 范围内对齐插件 framework logger 接入策略？ → A: 是，需补充宿主采集与策略编排对齐要求。
- Q: 宿主模式插件日志默认采集链路如何约束？ → A: 插件进程默认 stdout+json，并进入 PowerX 统一采集链路。
- Q: 平台是否必须支持插件 policy/probe 编排？ → A: 是，至少支持下发策略与变更探测闭环。

### Session 2026-10-15（系统快照与统一恢复）

- 面向管理员的备份与恢复单位统一为“系统快照／恢复点”，关联数据库、媒体实际内容、必要配置／密钥材料及 Core／插件版本。底层允许组件分别保存，不能让用户自行按时间配对。
- 一致性必须由采集边界、数据库事务快照、媒体内容版本及配置／版本锁共同保证；同 ID 或同时运行独立任务不等于一致。
- 系统快照完整性、异地保存、完整包导出和业务演练结果分别展示；单个组件 success 不代表整站可恢复或已完成正式切换。
- 跨环境完整包应在源实例不可访问时独立恢复。先本地状态 A → 快照 → 状态 B → 独立恢复 A，再升级服务器、观察真实定时任务并把自动快照带到本地／开发环境验收。
- 等一天用于验证真实调度；手动快照恢复不要求等待一天。恢复测试在启动前隔离生产连接、业务定时任务和外部业务写入。
- 统一正式切换需显式维护确认、当前环境回退点和持久化协调器；现有恢复到新库／新目录不具备此能力。
- 2026-04-10 的 `6h / 14 份 / 自动周演练` 为历史基线。现有新建数据库策略默认已为 `1h / 7 天 / 168 份`、策略及自动验证停用；这不代表线上现有策略已被调整，也不提前决定系统快照策略默认值。
- 详细设计：[系统快照计划](../../docs/plan/deploy/system-snapshot-and-restore.md)；实际能力见[托管整站恢复手册](../../docs/guides/deploy/027-monitor-center/usecase-us8-managed-recovery.md)和[本地证据](../../docs/contracts/evidence/system-snapshot-managed-validation-20261015.json)；尚未部署正式站，第二轮真实定时验收待执行。

### Session 2026-10-28（双环境存储治理）

- 同一台 120 GiB 主机上的正式、开发与共享资源统一纳管。以“保留目标＋容量预算＋保护条件”配置，先 observe，再 preview／受控执行，最后逐类启用自动治理。
- 初始主机日常预算 90 GiB、普通可用余量目标 20 GiB、10 GiB 紧急阈值；共享 PG／journal 只计一次，追踪／审计表额度属于数据库池子额度，不重复累加。
- 本地历史、远端已校验覆盖、预计可支撑时间分别展示。预算不足不静默缩短目标；有限空间不能承诺无限增长和任意断网期间的全部历史。
- PostgreSQL／journal 持续记录；活动、在途、待重试、仍有引用、法律保留与最低已验证恢复点受保护。journal 原生回收不等待异地确认，实际缺口必须可见。
- 存储治理使用桌面纵向分区与窄屏选择器，复用备份中心详情；异步任务用 WS／SSE，无页面状态轮询。
- [容量与生命周期设计](../../docs/plan/deploy/storage-governance.md)、[UI 设计](../../docs/plan/deploy/storage-governance-ui.md)、[实施验收](../../docs/guides/deploy/027-monitor-center/usecase-us9-storage-governance.md)为配套文档；[tasks.md 的 US9](tasks.md#us9-storage-governance)为任务状态唯一来源。新增 API、配置与来源合同仍待冻结，不代表已部署。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 配置并启用自动备份策略 (Priority: P1)

作为 Root 管理员，我可以在系统中设置自动备份计划（频率、保留数量、目标库/实例），并启用后由系统自动执行，无需人工每天手动触发。

**Independent Test**: 管理员可完成策略配置并观察到至少一次计划内备份成功执行。

### User Story 2 - 监控备份任务状态与历史 (Priority: P1)

作为 Root 管理员，我可以在监控入口中查看自动备份任务的当前状态、最近执行历史和关键统计，从而快速判断备份是否健康。

**Independent Test**: 管理员能在统一页面看到“计划任务 + 执行历史 + 成功失败状态”。

### User Story 3 - 快速演练恢复可用性 (Priority: P2)

作为 Root 管理员，我可以从指定备份记录触发一次恢复任务（不影响正式业务数据），并看到执行结论，以验证备份可用而非“仅有文件”。

**Independent Test**: 基于既有备份记录可发起恢复任务并拿到成功/失败结论。

### User Story 4 - 日志与链路追踪监控 (Priority: P1)

作为 Root 管理员，我可以在监控中心的日志页面按 trace/job/policy 查询日志，并根据当前日志驱动（loki/file/stdio）获得对应能力展示与跳转，从而快速定位备份与恢复问题。

**Why this priority**: 备份闭环已经可执行，但没有统一日志检索与链路关联会导致排障成本高。  
**Independent Test**: 不依赖恢复流程，仅通过日志页即可检索最近一次备份/恢复任务并定位关键错误。

**Acceptance Scenarios**:

1. **Given** 系统日志驱动为 `loki`，**When** 管理员进入日志页，**Then** 可按 trace_id/policy_id/job_id 检索并获得 Grafana 深链。
2. **Given** 系统日志驱动为 `file`，**When** 管理员检索日志，**Then** 返回本地日志内容并提示“不可用能力”（如无标签聚合）。
3. **Given** 系统日志驱动为 `stdio`，**When** 管理员检索日志，**Then** 返回 ring buffer 最近窗口数据并提示历史窗口受限。

### User Story 5 - 插件日志统一接入（Host 模式）(Priority: P1)

作为 Root 管理员，我可以让宿主模式下的插件日志统一进入 PowerX 日志采集链路，并对插件日志策略进行统一编排（policy/probe），从而保证跨 CoreX 与插件的链路排障一致性。

**Why this priority**: 监控中心已经提供日志检索能力，但若插件日志未稳定进入统一链路，跨系统定位仍存在盲区。  
**Independent Test**: 在宿主模式启用插件后，日志页可检索到插件 `plugin_id/tenant_uuid/component/level/trace_id` 字段并完成链路定位。

**Acceptance Scenarios**:

1. **Given** 宿主模式启用插件，**When** 插件输出结构化日志，**Then** 日志必须进入 PowerX 统一采集链路并可在监控日志页检索。
2. **Given** 平台下发插件日志策略，**When** 管理员执行策略探测，**Then** 系统返回各 sink 的 `success/failed/retrying/dropped` 结果并可审计。
3. **Given** 平台未授权额外 sink，**When** 插件处于 host 模式，**Then** 仅允许 `stdout+json` 默认生效，防止插件侧私自扩展出站。

### User Story 8 - 统一系统快照与跨环境恢复 (Priority: P1，部分实现)

作为 Root 管理员，我可以选择一个完整系统恢复点，由系统恢复数据库、媒体、配置和匹配版本，不需要在多个页面配对文件；我可以把服务器定时生成的完整包带到本地或开发环境验证，核验通过后再决定是否正式切换。

**Independent Test**: 本地创建状态 A，采集并导出 S，再形成 B；源实例不可访问时在独立目标恢复 A，源 B 保持不变。随后在服务器部署并取得真实 scheduled 快照，在另一环境完成同样的恢复验收。

**Acceptance Scenarios**:

1. **Given** 任一必需组件缺失、变更或校验失败，**When** 采集结束，**Then** 不能展示为完整系统快照。
2. **Given** 只有数据库 dump 或旧媒体配套归档，**When** 查看／导入，**Then** 明确组件范围，不按相近时间自动补成系统快照。
3. **Given** 完整包、独立解密材料及兼容目标，**When** 在空目标导入并断开源实例依赖，**Then** 数据、媒体、配置／绑定和应用功能均通过，且无生产连接或外部业务写入。
4. **Given** 媒体已复制但数据库／配置恢复失败，**When** 查询任务，**Then** 父任务失败并保留候选环境，正式站不变化。
5. **Given** 验证通过且管理员确认维护切换，**When** 执行失败或中断，**Then** 保持停写并按账本回退数据库、媒体、配置和版本，不能提供混合状态服务。
6. **Given** 服务器定时策略已启用，**When** 至少一个真实周期后导出 scheduled 快照，**Then** 可在本地／开发实例独立恢复并生成业务验收报告。

### User Story 9 - 双环境容量、历史窗口与生命周期治理 (Priority: P1，只读切片已实现，完整治理待完成)

作为管理正式与开发环境的 Root／运维人员，我可以查看主机及各类资源的实际占用、配置保留天数／份数与容量预算、核对本地和远端实际历史，并在保护业务引用与可用恢复点的前提下预览、执行和追踪自动清理，避免临时文件和历史记录无期限增长。

**Independent Test**: 在同一独立测试文件系统上登记两个实例和共享来源，完成只读对账、参数估算、预览及一轮受控执行；真实取回异地归档，证明活动数据、在途／重试记录和最低恢复点未误删。实际释放与逻辑删除分别记录；随后按阶段完成双环境自动周期及 XDocker 接管验收。

**Acceptance Scenarios**:

1. **Given** 两个实例共享 PG、journal 或 CAS，**When** 查看整机与环境视图，**Then** 唯一物理占用仅计一次，未覆盖来源显示未知，不能以预算或部分统计替代实占。
2. **Given** 示例每日高位增量为 0.30 GiB、余量系数 1.3，**When** 将 7 天／3 GiB 改为 14 天／3 GiB，**Then** 分别显示预计需要 2.73／5.46 GiB，后者缺 2.46 GiB 且不能启用，不静默调整用户目标。
3. **Given** 有上传租约、未完成事件、在途追踪、法律保留或最低已验证恢复点，**When** 资源过期或预算超限，**Then** 相应项仍受保护，显示阻塞与缺口，不扩大删除范围。
4. **Given** 两环境同时启动大任务或执行器崩溃，**When** 预留／恢复租约，**Then** 跨进程不超卖剩余空间，不依赖业务 DB 可用，状态和已执行部分可核对。
5. **Given** 远端断线、文件变化或 journal 已原生回收，**When** 查询历史或再次清理，**Then** 上传／校验／可取回状态与缺段真实显示，未校验本地数据不会被误报为已安全归档。
6. **Given** 桌面或窄屏页面正在编辑／执行，**When** 切换分区、断线重连或切换登录身份，**Then** 必要上下文保留，事件重连同步正确，旧身份连接释放且无周期状态查询。
7. **Given** 双环境分类自动治理通过，**When** XDocker 后续接管主机计量与预留，**Then** 仅一个主机权威协调者，策略、引用、审计和恢复能力保持一致，不自行授权任意宿主机命令。
8. **Given** 已登记正式、开发和共享来源，**When** 选择环境／实例及资源编辑草稿，**Then** 提供对应建议与保留方式（日志按天、备份／快照按份、媒体按引用保护），保存当前项不夹带其他环境未保存编辑；主机预算独立保存。未登记的环境不显示为可管理实例，旧组合草稿不自动转换。

### Edge Cases

- 自动备份执行时间到达时，上一轮备份仍在运行，系统如何避免重复执行和资源冲突。
- 存储空间不足导致备份中断时，系统如何标记失败并提示管理员介入。
- 保留策略触发清理时，若删除旧备份失败，系统如何保证新备份记录不丢失且告警可见。
- 时区变更或夏令时切换导致计划触发偏移时，系统如何保持预期执行节奏。
- 恢复任务目标环境不可用时，系统如何给出明确失败结论并防止误判为“备份可用”。
- 日志驱动从 `loki` 切换为 `file/stdio` 后，监控页如何降级展示并避免用户误解。
- `trace_id` 缺失或跨服务未透传时，日志页如何回退到 `policy_id/job_id/time-range` 检索。
- 采集时插件更新、配置变更、文件删除／覆盖、第三方写入未暂停，必须阻止封存不一致快照。
- 导出时源 CAS 缺对象、解密材料只在故障服务器、平台产物不匹配，不能宣称独立可恢复。
- 恢复时错选生产连接、缺扩展／配置／密钥、进程重启、磁盘不足、重复提交及切换部分完成，必须阻断或保持维护并执行可追踪补偿。
- 清理后的净磁盘增长不能代替每日新增量；采样不足、压缩率改变、采集无权限或历史断档时不能显示虚假可行／零占用。
- 预览后策略、路径、inode、活动状态或引用改变时重新校验；不根据过时预览删除。
- 普通 DELETE／VACUUM 未使操作系统空间下降时，应记录库内复用，不把删除行数换算成实际释放成功。
- journal 原生容量／时间回收先于远端确认、目标满或持续断网超过本地窗口时，必须暴露缺口，不承诺任意故障期间完整历史。
- 最新成功备份、最低已验证恢复点及显式保护本身超过预算时，告警并限制可延期的新大任务，不自动删除保护项。
- 新旧清理器、Core／独立 worker、PowerX／XDocker 同时运行时，必须唯一所有权与原子预算，避免重复处理和余量超卖。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持 Root 管理员创建、编辑、启用、停用自动备份策略。
- **FR-002**: 系统 MUST 对备份策略进行输入校验，并在非法输入时阻止保存。
- **FR-003**: 系统 MUST 按已启用策略自动触发备份作业，并记录每次作业的开始时间、结束时间、执行状态。
- **FR-004**: 系统 MUST 为每次备份作业生成唯一作业记录，确保可追踪到对应策略与租户上下文。
- **FR-005**: 系统 MUST 提供备份作业历史查询能力，支持按状态、时间范围、任务标识筛选。
- **FR-006**: 系统 MUST 在监控入口展示自动备份任务的当前状态、下次执行时间、最近执行结果与失败摘要。
- **FR-007**: 系统 MUST 在备份失败时生成可见告警信息，包含可操作的排查提示。
- **FR-008**: 系统 MUST 支持从备份记录触发恢复任务，并可查看执行进度与最终结论。
- **FR-009**: 系统 MUST 在自动备份与恢复操作中保留完整审计轨迹（操作者、时间、动作、结果）。
- **FR-010**: 系统 MUST 支持保留策略，能够在不破坏最新可用备份的前提下清理过期备份产物。
- **FR-011**: 现有数据库策略默认频率为每 1 小时，策略默认停用；允许管理员覆盖。系统快照策略默认值在实现合同中明确，不改变历史策略。
- **FR-012**: 现有新建数据库策略默认保留 7 天、最多 168 份，并保护最新成功备份和显式保留项；统一快照必须按整套组件引用保留。
- **FR-013**: 数据库自动恢复验证默认关闭，启用后的默认间隔为 7 天；可手动触发。组件自动验证不能充当整站业务恢复验收。
- **FR-014**: 系统 MUST 在备份连续 2 次失败时自动升级为高优先级告警，并在监控入口突出展示。
- **FR-015**: 系统 MUST 以 Asia/Shanghai 作为默认调度时区，并允许 Root 管理员按策略覆盖时区配置。
- **FR-016**: 系统 MUST 提供日志配置查询接口，返回当前驱动类型（`loki/file/stdio`）与能力矩阵。
- **FR-017**: 系统 MUST 提供统一日志查询接口，至少支持 `trace_id/job_id/policy_id/time_range/keyword` 过滤。
- **FR-018**: 系统 MUST 在 `loki` 驱动下支持标签检索与 Grafana 深链（可按 trace/job 跳转）。
- **FR-019**: 系统 MUST 在 `file` 驱动下支持基于文件的时间窗口检索，并明确不可用能力。
- **FR-020**: 系统 MUST 在 `stdio` 驱动下支持最近窗口（ring buffer）检索，并提示历史窗口限制。
- **FR-021**: 监控中心 Logs/Trace 页面 MUST 根据驱动能力动态渲染，不得展示不可用操作入口。
- **FR-022**: 日志查询与跳转能力 MUST 仅对 Root 管理员开放，并记录审计日志。
- **FR-023**: 当日志驱动不可用或查询失败时，系统 MUST 返回可操作错误提示（驱动状态、建议步骤、trace_id）。
- **FR-024**: 系统 MUST 提供统一日志保留策略入口 `log.retention`，覆盖文件日志与数据库日志清理策略（按来源可配置 retention 与执行计划），避免仅依赖 rotate 导致总量不可控。
- **FR-025**: 系统 MUST 提供日志保留任务执行记录与审计信息（执行时间、清理来源、删除数量、状态、失败原因），供监控中心查询与告警使用。
- **FR-026**: 系统 MUST 在宿主模式下确保插件进程日志默认进入统一采集链路（stdout+json），不得因默认配置导致插件日志仅保留于进程内缓冲。
- **FR-027**: 系统 MUST 提供插件日志策略编排能力，至少覆盖 `GET/PUT policy` 与 `POST probe` 的平台化调用与审计记录。
- **FR-028**: 系统 MUST 对插件日志标签执行低基数约束，固定标签至少包括 `plugin_id/tenant_uuid/component/level`；高基数字段仅保留在日志内容中。
- **FR-029**: 系统 MUST 保证 `trace_id/tenant_uuid/plugin_id/component/level` 在采集、转发、检索链路中可用且不丢失。
- **FR-030**: 当插件日志策略变更或 sink 不可用时，系统 MUST 给出可操作探测结果与降级状态，且不阻断主业务链路。
- **FR-031**: 系统 MUST 在宿主 HTTP 最外层统一解析并注入 `plugin_id`，至少覆盖 `/_p/<plugin_id>/...` 与 `/api/v1/integration/<slug>/...` 两类路径；其中 `<slug>` 必须通过稳定映射解析为 `plugin_id`。
- **FR-032**: 系统 MUST 让以下日志源统一从同一上下文读取 `request_id/trace_id/plugin_id/tenant_uuid`：`http_request`、`audit_event`、`API-IN/GATE-*/PROXY-*`、`wsbus.*`、插件 supervisor 日志、异步 worker（cron/queue/retry/event-fabric）。
- **FR-033**: 系统 MUST 在异步链路禁止无条件使用 `context.Background()` 覆盖原请求上下文；若上下文缺失，sink 层必须执行字段兜底回填（事件 payload/meta/响应头）并记录 `reason`。
- **FR-034**: 系统 MUST 将 `plugin_id/request_id/trace_id/tenant_uuid` 作为日志顶层字段输出，禁止仅写入 `meta` 字符串；`meta` 仅用于扩展诊断信息。

#### 统一系统快照要求（含后续未完成范围）

- **FR-035**: 系统 MUST 以一个 `snapshot_id` 和父任务绑定数据库、媒体、必要配置／密钥材料、程序及插件版本；所有必需组件齐全并校验后才显示完整恢复点。
- **FR-036**: 普通手动／定时采集 MUST 在线执行，不暂停业务写入、不停止 Core／插件、不锁表阻止 DML；数据库与登记为 ready 的媒体引用共享 MVCC。并发文件变化必须阻止错误封存并有界重试（最多 4 次），配置与插件生命周期须指纹校验。未具备 Redis 跨组件一致性协议的在线包 MUST 标为不可直接整站切换，不能冒充完整业务恢复点；正式切换回退点仍在维护确认后采集。
- **FR-037**: 系统 MUST 区分快照完整性、异地状态、导出状态与业务验证结果；仅数据库／媒体备份不能计入最近完整系统快照。
- **FR-038**: 系统 MUST 支持多套命名策略的表格维护，任一时刻只有一套默认策略可启用并统一调度所有必需组件；允许全部停用。默认切换原子停用上一套，展示真实周期、下次执行、失败阶段和告警，按快照所属策略及整套引用执行保留与 GC。
- **FR-039**: 系统 MUST 提供独立完整包导出／导入，包含全部引用内容或已解析核验的对应产物；不依赖源实例、未随包提供的增量链或生产 URL。
- **FR-040**: 系统 MUST 加密保存必要敏感配置，提供独立解密材料的恢复路径；不在清单／日志暴露密钥，不把唯一解密材料留在被备份库中。
- **FR-041**: 系统 MUST 在恢复前检查格式、解密、完整性、空间、扩展、程序／迁移版本、驱动、平台和目标身份／绑定映射；不支持项阻断，不静默遗漏。
- **FR-042**: 系统 MUST 支持本地／开发隔离恢复，使用新库、新媒体根目录与目标配置；在 Core／插件／worker 启动前禁用生产连接、业务定时任务、队列消费和外部业务写入。
- **FR-043**: 系统 MUST 以一个恢复父任务聚合数据库、媒体、配置及应用验证，全部必需检查通过后才进入待确认切换状态。
- **FR-044**: 正式恢复 MUST 在明确维护确认后暂停全部写入，保存当前回退点并统一切换数据库、媒体、配置和版本；使用不依赖被停止 Core 或被恢复业务库的持久化协调器。
- **FR-045**: 系统 MUST 为切换失败、中断与重复请求提供账本、幂等和整套补偿；恢复写入后的回退不得宣称无损自动执行。
- **FR-046**: 整站快照导出、导入、恢复和正式切换 MUST 仅允许平台 Root 用户 JWT；拒绝普通租户、STS 和插件 API Key，记录必要审计且不接受任意 shell／SQL／DSN／服务器路径。
- **FR-047**: 系统 MUST 保持旧策略及产物原类型可用，不自动拼接、停用或修改线上周期；新系统快照接口在正式合同冻结并实现后才能发布。
- **FR-048**: 交付 MUST 通过本地 A／B 恢复与失败演练，以及部署后真实 scheduled 快照跨环境恢复两轮验收，保留组件、业务与源环境未改变的证据。

#### 双环境存储治理要求（US9，待实现）

- **FR-049**: 系统 MUST 登记稳定的主机、文件系统、部署实例、环境、租户和资源身份，区分共享与实例拥有资源，不根据目录或自由名称猜测身份。
- **FR-050**: 系统 MUST 提供只读整盘计量和覆盖信息，区分逻辑／物理／压缩占用、数据库表／索引／TOAST／WAL、文件系统预留和普通可用；硬链接及共享 CAS 不重复计量，未知不填 0。
- **FR-051**: 系统 MUST 支持主机池与资源子额度，按 120 GiB 双环境设计基线评估 90 GiB 日常预算、20 GiB 余量和 10 GiB 紧急阈值；子额度不得重复加入主机总账，治理预算不得冒充数据库或文件系统原生硬限额。
- **FR-052**: 系统 MUST 用明确采样口径、14 天窗口、样本覆盖与余量估算“保留目标／容量预算”的缺口；无样本、口径改变和采集失效时显示待采样／不可估算，不自动修改已保存天数与额度。
- **FR-052a**: 策略编辑 MUST 绑定部署登记的环境／实例和资源类型；主机总预算与资源子额度分别编辑，环境建议不覆盖已保存值。按份数或引用保护资源不能套用按天增量公式；实际产物清单未接入时返回不可估算。保存单资源不得提交其他资源未保存的编辑。
- **FR-053**: 系统 MUST 分开记录目标期限、实际本地历史、远端已校验可取回覆盖及预测时间，并展示缺段，不以最早／最近时间或刚保存的 90 天策略冒充连续历史。
- **FR-054**: 自动清理 MUST 只处理已登记、满足过期与保护规则的资源；活动、引用、法律保留、在途／重试和最低恢复点优先，超预算时告警并限制可延期任务，不默认缩短目标或删保护项。
- **FR-055**: 追踪、事件和审计 MUST 使用按真实模型冻结的类型化终态／时间／引用适配器，受租户边界、批次、锁等待和 WAL 压力限制；不能直接套用通用按创建时间删表规则。
- **FR-056**: 上传、导入导出与插件附件暂存 MUST 有受控工作区、大小限制、持久租约与正常／取消／崩溃收尾；异步移交后不能继续依赖请求级临时文件；永久业务媒体不能套用普通 TTL 删除。
- **FR-057**: PG 日志 MUST 排除实际活动文件并在稳定封存、压缩、异地校验后按规则回收；journal MUST 有游标／boot 边界和覆盖账本，原生回收造成的缺口必须明确报告；相关日志参数及重启不能自动随文档生效。
- **FR-058**: 归档 MUST 支持版本化压缩对象、原内容与存储哈希、旧对象读取和物理计量；远端保留、清单、namespace、重试及取回分别核验，不以 SSH 连通替代归档成功。
- **FR-059**: 备份／快照 MUST 在天数／份数之外支持字节预算与最低可用／已验证恢复点保护，全部对象引用和 GC 互相协调；ready、文件存在、具备恢复能力、恢复验证不能混同。
- **FR-060**: 高占用任务 MUST 在每个写入文件系统获得跨正式／开发、Core／worker 的原子峰值预留，计算普通可用空间、有效未写预留和 20 GiB 余量；不得只依赖进程内锁或单一 128 MiB 局部假设。
- **FR-061**: 预算与租约 MUST 支持幂等、续期、写入转实占、取消、崩溃恢复及独立于业务 DB 的受控持久状态，避免预留泄漏与重复扣减。
- **FR-062**: 清理 MUST 提供带版本、候选指纹、有效期与保护原因的预览及执行前复核，有限批次／时长、可取消；已接受、执行中、部分完成、待核验和最终结果分别记录。
- **FR-063**: 系统 MUST 分别报告预计回收、实际逻辑删除、库内可复用、物理已回收与整盘净变化，审计和任务账本自身有容量／保留限制；不得以 VACUUM FULL、删 WAL 或关闭日志作为自动达标手段。
- **FR-064**: 新主机治理 API MUST 首期仅允许 Root 用户 JWT，通过真实路由验证范围与操作授权；拒绝调用者提交任意路径、SQL、shell、DSN 或代理载荷，API Key／STS 不套用管理员权限。
- **FR-065**: 存储治理 UI MUST 提供容量概览、保留策略、归档追溯、清理记录和告警分区，桌面纵向导航、窄屏选择器；保留草稿与任务上下文，关键错误跨分区可见，复用备份详情而非复制权威策略。
- **FR-066**: 任务 MUST 复用统一 TaskBus／业务调度和 WS／SSE 推送；支持事件去重、版本、断线重连快照与身份变更释放连接，不得使用页面周期状态轮询。
- **FR-067**: 升级 MUST 默认只读 observe，保留旧策略值，并协调新旧资源清理所有权；普通日志转发失败不阻塞业务，可靠审计另设交付合同。XDocker 后续接管必须保持唯一主机预留权威及业务保护，正式服务能力按合同单独授权。
- **FR-068**: 交付 MUST 按 observe → preview → 受控执行 → 分类自动化完成本地及双环境验收，包含真实远端取回、业务／插件、故障注入、至少 7 天自动周期及 14 天样本后预算复核；不能以 CI、截图或旧任务完成替代新增验收。

### Key Entities *(include if feature involves data)*

- **BackupPolicy（备份策略）**: 描述自动备份规则，包括启停状态、执行频率、保留策略、生效范围。
- **BackupJob（备份作业）**: 一次实际备份执行实例，包含执行窗口、状态、结果摘要、错误信息。
- **BackupArtifact（备份产物）**: 备份作业生成的可恢复数据集合标识，包含可用性状态与过期信息。
- **RestoreJob（恢复任务）**: 基于备份产物执行的恢复任务，包含目标环境、执行进度、任务结论。
- **BackupAlert（备份告警）**: 针对失败、延迟、清理异常等事件的告警记录，用于监控视图聚合展示。
- **MonitorLogConfig（日志配置）**: 当前日志驱动配置与能力矩阵快照。
- **MonitorLogEntry（日志条目）**: 监控页可查询的结构化日志记录，包含时间、级别、模块、trace_id、消息体。
- **SystemSnapshotPolicy / SystemSnapshot / SnapshotComponent（本地实现）**: 统一调度、完整恢复点与组件内容版本。
- **SnapshotPackageJob / SystemRestoreTask（本地实现）**: 完整导入导出，以及目标映射、联合验证、正式切换和回退账本。
- **StorageResource / FilesystemObservation（US9，拟新增）**: 稳定来源身份、归属、唯一物理计量、覆盖与采样时间。
- **StorageBudget / RetentionPolicyRevision（US9，拟新增）**: 主机池／子额度、天数或份数、保护条件、版本与启用状态。
- **SpaceReservation / WorkspaceLease（US9，拟新增）**: 跨实例任务峰值预留、引用、续期与崩溃接管账本。
- **CleanupPlan / CleanupRun（US9，拟新增）**: 可复核预览、幂等执行、保护跳过、逻辑与物理结果及审计。
- **ArchiveCoverage（US9，拟新增）**: 本地与远端覆盖、游标／封存边界、校验与可取回证据、缺失区间。

## Assumptions

- 自动备份、恢复任务与日志检索均仅对 Root 管理员开放。
- 备份产物已具备统一命名与存储位置约束，策略层不重复定义底层存储协议。
- 恢复任务默认在隔离环境执行，不直接覆盖生产业务数据。
- 系统快照不等于云盘镜像或 PITR；首版以 PostgreSQL + 本地媒体为基线，未覆盖的持久依赖必须显式阻断完整恢复声明。
- 日志驱动由系统配置决定，监控页按运行态能力动态降级。
- US9 的固定本地空间只承诺在已验证负载／准入条件下的有界目标；永久业务数据增长或长时间远端失联仍需告警、预算调整或扩展，不能承诺任意负载永不满盘。
- US9 初始数值是待实施基线，不改变现有线上保留策略、collector、timer 或数据库结构。

## Dependencies

- 需要存在可用的备份执行环境与存储目标。
- 需要调度能力稳定运行，以保证计划任务按时触发。
- 需要审计与日志能力可用，以支持失败排查与合规留痕。
- 若驱动为 `loki`，需要 Loki API 与 Grafana 地址配置可用。
- 需要插件运行时可由宿主注入并识别 host 模式信号（`POWERX_PROXY=1`）以及统一日志策略接口。
- US9 依赖已登记来源与权限、独立且可取回的远端、跨进程预算／租约和真实业务状态合同；XDocker 的主机／卷／预留协议仍需对接，不假定已实现。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Root 管理员可在 3 分钟内完成自动备份策略创建并启用。
- **SC-002**: 启用后的自动备份策略在连续 7 天内按计划触发率达到 99% 及以上。
- **SC-003**: 备份失败事件在 1 分钟内可在监控入口被识别并查看失败摘要。
- **SC-004**: 管理员在监控入口定位最近一次备份任务状态的平均时间不超过 30 秒。
- **SC-005**: 任意一次恢复任务在结束后 1 分钟内可查看明确结论（成功/失败）与原因摘要。
- **SC-006**: 日志页在 10 秒内返回最近 15 分钟内的备份链路日志（同城网络条件）。
- **SC-007**: `loki/file/stdio` 三驱动下，监控页均可正确展示可用能力与不可用能力提示，误点击率为 0。
- **SC-008**: 宿主模式插件启用后，95% 以上插件日志在 1 分钟内可进入统一日志检索链路。
- **SC-009**: 插件日志策略变更后，`policy/probe` 联调链路在 3 分钟内可完成并返回可审计结果。
- **SC-010**: 对同一次 `/api/v1/integration/<slug>/...` 请求，使用同一个 `request_id` 可在 `http_request`、`audit_event`、`API-IN/GATE/PROXY-*`、`wsbus.*` 中命中，且 `plugin_id` 非空。
- **SC-011**: 所有必需组件缺失／校验失败用例均不能产生完整可恢复系统快照。
- **SC-012**: 源实例不可访问、目标为空时，完整包恢复通过全部已登记媒体引用校验及关键业务断言。
- **SC-013**: 本地 A／B 演练中目标为 A、源仍为 B；隔离目标无生产连接和外部业务写入。
- **SC-014**: 数据库或配置失败时父任务不报成功；切换失败／中断演练中不提供混合组件状态服务。

- **SC-018**: 0.30 GiB／天与 1.3 倍示例下，7 天和 14 天预计需要 2.73 和 5.46 GiB；14 天／3 GiB 不能启用，不改变目标值，采样不足有明确状态。
- **SC-019**: 多实例／多进程并发、重复请求和崩溃接管测试中，获准任务全部满足其文件系统预留与余量规则；预览后新增引用不被删除。
- **SC-020**: 活动文件、在途追踪、待重试事件、法律留置、显式保留及最低已验证恢复点保护用例无误删；逻辑删除不冒充操作系统物理释放。
- **SC-021**: 至少一次真实异地传输、对象／清单校验和带离源机取回／恢复通过；断网及原生 journal 回收的缺口不会被报告为完整覆盖。
- **SC-022**: 桌面及 390／320 px 浏览器流程中导航、草稿和主要操作可用；无事件静置时没有周期状态请求，重连及身份切换无旧连接泄漏。
