# PowerX 插件数据集生命周期治理

状态：Core 实施与 Framework 对接。业务插件按平台合同独立接入。任务进度在 [US9／SG-12](../../../specs/027-monitor-center/tasks.md#us9-sg-12) 维护。

登记和预览见 [T175 合同](../../contracts/plugin-dataset-lifecycle-review.md)。单次批次授权、源账本与归档取回见 [T178～T179 执行合同](../../contracts/plugin-dataset-execution.md)。

平台运维人员在「存储治理」查看系统与插件数据集的占用和增长，了解哪些记录受保护，预览策略影响，再为符合条件的数据集启用保留策略。插件团队定义业务边界，常见数据集共用 Framework 执行器。需要业务判断时，插件只实现资格检查和并发保护，调度、限额和结果核对仍由平台统一管理。

## 1. 现有能力与接入边界

Core 现有系统表目录只用于观测。调用日志期限策略覆盖调用追踪和事件发布两类表，专项策略覆盖健康探测历史和退休发现缓存。现有规则、策略版本、回执和调度继续由原控制域管理。统一目录通过内置适配器展示这些资源，首期只读关联现有策略，避免同一数据集出现第二个写入口或第二个清理任务。 [系统表目录](../../../backend/pkg/corex/db/persistence/model/storage_governance/system_table_catalog.go) · [调用日志合同](../../contracts/database-retention-control.md) · [专项系统表合同](../../contracts/system-table-retention-control.md)

| 责任方 | 负责事项 |
|---|---|
| Core | 认领数据集和来源、统一目录、容量告警、策略启停与版本发布、正式 TaskBus 调度、执行结果及运维审计 |
| Framework | 声明格式、类型化 SDK、在数据源侧运行的共享执行器、租户隔离、事务、超时、批次、执行围栏和回执上报 |
| 插件 | 数据集边界、到期起点、终态和保护条件，维护必要索引、业务去重窗口及引用写入协议，按需提供业务保护适配器 |

执行位置由数据源决定。Core 内置规则沿用现有 Core 执行路径。插件数据由插件运行环境内的 Framework 执行器使用该来源的受限连接处理，共库或独立 PostgreSQL 使用相同的任务合同。Core 通过安装和运行时登记解析目标执行器。插件停用、排空、卸载或执行器失联时，插件数据的写批次停止准入，目录保留最后采样时间和退出原因。

## 2. 数据集身份和持久化

治理对象是一组具有共同生命周期的记录，可以包含主表及附属明细。稳定的 `dataset_uuid` 用于管理接口、事件、策略和回执。Core 根据部署作用域、所有者类型、经核验的所有者标识、逻辑数据源绑定和 `dataset_key` 保证唯一。同一插件升级时保留数据集 UUID，安装版本、声明版本、策略版本和数据源指纹分别记录。一个逻辑数据集绑定一个数据源。需要跨库保护引用的对象先按保护数据接入。

| 信息 | 权威与处理方式 |
|---|---|
| Core 内置数据集 | 从固定代码目录投影，用固定键解析到稳定 ID，保留现有物理表 ID 供原调用方使用 |
| 插件数据集声明 | 随已安装版本交付。Framework 提交声明标识、合同版本和摘要，Core 与安装清单核对。同一请求 UUID 和内容重复提交，返回原结果。旧安装版本和旧合同不能覆盖当前接纳结果 |
| 插件数据源 | 优先解析安装记录及 Host 数据库配置的 `binding_uuid`，核对部署环境、插件归属和允许访问的 schema。独立 PG 同样需要可信的绑定记录，插件请求只能引用已有绑定 |
| 数据集接纳 | 拟新增 `ops_storage_datasets`，记录稳定身份、当前接纳快照、来源、合同摘要和接纳、失效或退役状态。已生效策略和历史回执保留当时使用的版本及摘要 |
| 策略与发布 | 复用全局执行控制。插件数据集的租户级策略、接纳版本和在途回执写入 `ops_storage_cleanup_runs` 的独立命名空间。策略通过乐观修订和行级互斥保存 |
| 观测与回执 | 复用现有采样与运行账本机制。给插件采样增加按来源隔离的指标口径，保留原系统表的历史口径。跨库执行的源端持久回执由执行合同单独处理 |

现有 `plugin_instance_configs` 用于租户与插件的启停和配置，安装 Registry 提供已安装版本。现有 `ops_storage_policies` 用于实例级策略草稿。部署凭据仍由已有受控配置保存，目录、策略、任务、回执和日志只记录标识或不可逆摘要。 [插件数据库隔离设计](plugin-database-isolation.md) · [控制事务模型](../../../backend/pkg/corex/db/persistence/model/storage_governance/control_gorm.go) · [插件租户配置模型](../../../backend/pkg/corex/db/persistence/model/setting/plugin_instance_config_gorm.go)

## 3. 声明内容及治理分类

| 字段 | 约束 |
|---|---|
| `dataset_key`、`contract_version`、`schema_contract_version` | 数据集稳定键和明确版本。同版本、不同摘要返回冲突 |
| `source_binding_ref`、`tenant_scope` | 声明使用可移植的逻辑来源键，由 Host 解析为实际绑定。插件首期为租户数据集，每个处理批次绑定一个经过核验的租户 |
| `adapter_key`、`adapter_version`、成员对象 | 解析到已安装版本中登记的类型化适配器。适配器声明根对象稳定键、成员关系、索引及处理顺序 |
| 到期起点、可处理终态、保护条件 | 由插件业务合同定义。保留期从明确到期起点计算，时间缺失、状态不识别或引用无法确认时跳过 |
| `allowed_actions`、保留范围、默认建议 | 明确允许观测、归档或删除，以及是否必须先归档。插件默认期限仅作建议，Core 校验管理员配置未超出允许范围 |

来源绑定、租户、表结构、索引、候选谓词和业务保护均在受控适配器中解析和核验。声明和接口不接受连接串、调用方任选的 SQL、过滤表达式或代理地址。标准执行器只实现预先定义的策略类型。复杂数据由插件复用相同的执行框架并提供业务适配器。

页面分别显示**容量风险**和**允许处理方式**。容量使用表、索引、TOAST 占用和同口径的净增长，断档或来源变化后重新建立增长基线。共享物理表按真实来源和物理对象只计算一次，租户候选数量与物理容量单独标记。PostgreSQL 物理膨胀走数据库空间维护，过期业务记录走期限治理。 [现有表容量监控](../../contracts/storage-table-monitoring-control.md) · [数据库空间维护](../../contracts/database-space-maintenance.md)

| 业务用途 | 首批处置 |
|---|---|
| 合成插件报告及明细 | 平台验收样本，由 Core 和 Framework 自行构造。覆盖过期无引用、过期仍被引用、最新有效、内容不完整和无法核验的记录 |
| 真实回归执行报告及断言明细 | 可按保护类先登记和计量。业务插件核对完整性、最新有效结果、批次与证据引用和正式留存后，才开放该数据集的预览资格 |
| 运行轨迹与回归用例 | 两类数据分开登记。回归用例的 `source_run_uuid` 证明存在轨迹引用，受引用轨迹、用例及基线保留。轨迹开放处理前补齐引用创建与清理的共同约束 |
| LLM 任务与投递 | 先观察。AI Craft 现有 `failed` 可重新运行，适配器需核对租约、投递、重试与去重保留。历史任务删除后仍须满足原有业务幂等约定 |
| 客户消息、业务审计及交易主记录 | 保护类，仅观测并说明原因。业务留存、引用和归档可恢复性明确后，另行定义该数据集允许的动作 |

## 4. 接口、权限和状态

Core HTTP 路径使用部署配置的 API 前缀。 [API 路径与版本规范](../../standards/_shared/api-prefix-and-versioning.md)

| 调用方 | 接口与权限 |
|---|---|
| PowerX Root | 新增 `GET /admin/ops/storage/datasets`、`GET /admin/ops/storage/datasets/{dataset_id}`。按来源、插件、容量状态和可用动作筛选。原系统表管理和清理路由沿用现有合同 |
| PowerX Root | 插件数据集首期提供 `POST /admin/ops/storage/datasets/{dataset_id}/previews` 及原预览查询。策略修订、启停、单次运行与回执接口见执行合同 |
| Framework 登记服务 | 现有 tenant invocation 入口调用固定 `core_internal`、`core://storage-governance/datasets`、`INVOKE` 绑定。用类型化登记操作和 STS 服务身份，校验已发布能力、租户登记及插件归属。首期服务授权限定登记自己的声明 |
| Core 调度与 Framework 执行器 | Core 经正式 TaskBus 向已核验的服务执行器下达通知。Framework 持原任务租约向 Core 领取固定的数据集、来源、租户、版本、截止时间和范围，按原任务上报 |

Root JWT／RBAC 和服务身份保持独立。Root 管理入口保留平台级角色校验。服务能力的正式声明包含其对应的授权平面、类型化操作、权限码、风险级别，且 `agent_usable: false`。首期通过 STS 验证，Local Host API Key 支持如纳入后续范围，需先补精确 API Key 元数据、显式 IAM 权限和当前授权验证。现有整机控制继续使用 Root 接口。 [Capability 规范](../../../.codex/skills/governance/capability-governance/SKILL.md) · [现有 Root 路由](../../../backend/internal/transport/http/admin/storage/api.go)

登记输入拟包含 `request_uuid`、`dataset_key`、`definition_version`、`definition_digest` 和逻辑来源引用。部署、租户、插件身份及当前安装版本由有效身份与安装记录确定。接纳结果返回 `dataset_uuid`、接纳版本、状态和原因码。来源尚不可验证时可保留待校验记录，越权或摘要冲突应直接拒绝。只读预览返回候选数量及是否为有界估算、保护理由汇总、截止时间、预览有效期和绑定版本。目录或预览不展示业务记录正文。

登记接纳、观测、策略与运行是四个独立状态。登记可以待校验、已接纳、需重新校验或已退役。观测可以正常、过期或不可用。策略可以暂停、待发布或已启用。运行可以完成、部分完成、失败或待核对。升级改变来源、结构、适配器或保护条件时，旧预览和执行版本失效，重新核验后由管理员启用。数据源迁移、恢复或卸载均核对安装归属和来源代次。退役保留可追溯的记录，不触发源数据删除。

## 5. 调度、执行和归档

1. Core 验证接纳状态、当前策略版本、全局执行开关、租户启用状态和来源，按经确认的预览派发有界任务。预览固定截止时间、版本和范围，允许持久化预览凭据，源数据只读。首次实际启用前由 Root 核对预览。
2. Framework 在数据源侧核验任务归属、适配器、结构及执行租约。每批检查紧急停用和当前版本。对逻辑删除设置批量、扫描范围、周期、锁等待及超时限额，适配器按稳定游标扫描，实际执行重新验证候选。保护判定和数据变更必须在同一事务。引用创建或业务重试需遵循同一个约束或状态门禁，单次查询无引用不足以开放处理。
3. Core 内置适配器沿用现有同库事务。插件执行器在源端事务同时提交数据变更、批次持久回执及待上报记录，再经正式交付机制汇总到 Core。该机制同时适用于插件共库与独立 PG。源库批次账本及持久交付的复用或迁移范围在 T175 评审。派发、执行与上报重放沿用原批次 UUID，重复任务读取原回执。同一 UUID 携带不同范围或版本返回冲突。无法确认结果时进入待核对，暂停该范围的后续写批次，由原 UUID 查证。
4. 暂停后立即停止新派发和新授权。已签发授权使用固定的短时限及不可重复的批次围栏。源端拒绝过期执行者提交。Core 展示源端暂停是否确认，以及已接纳批次是否排空。联系不上源端时按短时租约和有界事务收敛，并保持可见的待确认状态。升级或恢复后，重新验证当前版本与执行代次。
5. 需要归档的数据集由 Root 选择已校验目标，Core 写入固定的版本化对象并核对内容及可取回性。归档回执属于原批次。要求先归档的声明保持源数据保护，等成员与引用证明合同明确后开放下一步。失败、版本变化或结果未知时保留源记录。归档可以独立完成，过期对象的回收另遵循目标和恢复保护合同。 [归档目标控制](../../contracts/archive-target-control.md)

页面沿用「存储治理」，独立目录分区显示来源、容量和可用操作。点击查看保留预览，再进入执行策略与批次。窄屏使用分区选择器。切换分区保留筛选、草稿和原请求编号，阻塞状态在各分区可见。异步状态由正式 SSE／WebSocket 推送，初次读取、手动刷新、事件和重连可触发同步。

## 6. 实施顺序与验收

| 阶段 | 依赖与通过条件 |
|---|---|
| T175 平台合同 | Core 主责冻结登记、任务授权、只读扫描守卫、保护结果和最小迁移规则 |
| T176 登记和只读目录 | Core 用固定系统数据集和合成插件数据集，验证接纳、重复登记、来源变更、共享计量去重和原系统表控制域 |
| T177 只读预览 | Core 与 Framework 用合成插件验证派发、领取、扫描、上报及事件更新。覆盖任务伪造、租约、结果对账和未知资格受保护 |
| T178 删除与回执 | 在隔离同库、独立 PG 中验证一个满足保护要求的插件数据集。覆盖并发引用和重试、过期租约、暂停排空、业务事务回滚、提交后响应丢失、重复上报与回执核对。已有系统任务继续由原执行路径运行 |
| T179 归档与受保护数据 | 先完成真实目标校验和恢复取回，再复核 LLM 任务、会话消息及业务审计能开放的具体动作。发布、实际策略接管和运行验收各自记录证据 |

Core 的实施 worktree 为 `PowerX-storage-datasets`，分支为 `feat/storage-datasets`。Framework 按 Core 合同接入共享 SDK 和执行器。AI Craft 或其他插件的业务适配在各自接入时由对应仓库交付。现场迁移、服务重启、策略启用与生产清理按实际维护窗口单独安排。
