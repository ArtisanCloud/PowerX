# 核心 Flow 与智能体 Workflow 的区别

## 为什么需要区分
核心平台的「Flow」能力与智能体层的「Workflow」编排都涉及步骤编排，但它们解决的治理问题完全不同。明确边界可以避免把基础设施级的自动化与面向租户的业务流程设计混为一谈。

## 对比概览
| 维度 | 核心平台 Flow（事件与任务流管理） | 智能体 Workflow（智能体编排） |
| --- | --- | --- |
| 使命 | 提供稳定可靠的事件管道与任务执行，支撑底座服务协同。 | 以租户为中心建模业务流程，协调智能体、插件与人工审核。 |
| 触发方式 | 系统事件、消息总线订阅、调度器、重试队列等。 | 通过画布、API 或人工触发携带上下文的业务意图。 |
| 典型角色 | 平台运维、SRE、消息总线运营者、调度服务。 | 工作流设计者、租户管理员、方案工程师、审计人员。 |
| 可靠性关注点 | 幂等、退避与重试、死信处理、基础设施级熔断。 | 模板版本管理、条件分支、人工参与检查点、租户级回滚。 |
| 交付物 | 稳定投递管道、弹性任务处理器、可审计的事件追踪。 | 可部署的工作流蓝图、运行监控看板、面向租户的变更记录。 |

## 分层协作模式
1. **Flow 作为底座** —— 事件枢纽、调度器与延迟队列发布任务或状态变更，供智能体订阅。
2. **Workflow 负责业务组合** —— 智能体工作流消费这些事件，串联核心动作、插件能力、自定义逻辑，并沉淀上下文审计记录。
3. **闭环反馈** —— 工作流的执行结果（成功、人工升级、回滚）再向 Flow 层回推事件，完成监控与自动化闭环。

## 治理检查清单
- 制定**平台策略**时，优先使用 Flow 原语：重试、限流、熔断、审计追踪。
- 交付**租户体验**时，依赖 Workflow 构件：节点目录、拖拽式编排、审批任务、发布通道。
- 打通观测体系：将 Flow 层的追踪数据（消息 ID、投递延迟）与 Workflow 层的运行记录（实例 ID、分支路径）关联，便于端到端排障。
- 建立变更管理：Flow 改动遵循基础设施发布闸口；Workflow 改动遵循模板版本管控与租户分批发布计划。
