# 受控存储任务执行保护

2026-11-07，SG-11 的紧急暂停与交接锁定切片。[操作手册](../guides/deploy/027-monitor-center/usecase-us9-storage-execution.md)、[OpenAPI](../../specs/027-monitor-center/contracts/execution-control.openapi.yaml)、[隔离验收](evidence/storage-execution-control-validation-20261107.json)。整个 SG-11 仍未关闭。

## 作用范围

当前 host／filesystem／instance 范围的固定 `execution-control` 域复用现有配置、不可变版本和正式 TaskBus。没有新表、启动迁移、自动接管或外部进程管理。

首次配置前为 `unmanaged`，保留现有资源规则，UI 明示未接入全局保护。首次操作只能暂停或开始交接。此后，新版受控普通计划的以下入口先核验执行开关，再核验资源权威：

| 执行入口 | 受控步骤 |
| --- | --- |
| 文件生命周期 | 逐文件最终提交守卫 |
| 归档策略 | 接纳、传输、远端批次回收、本地保留 |
| 数据库备份计划 | 计划作业接纳、逐产物保留清理 |
| 普通系统快照计划 | 采集接纳、自动包清理 |
| 调用日志期限 | 固定适配器批次／预览事务 |
| 两项专项系统表期限 | 固定适配器批次／预览事务 |

已经接纳的排队／长任务可能继续完成；不能将全局暂停称为自动取消、排空或中断 pg_dump。Root 显式维护、独立恢复／维护采集、业务媒体写入、旧二进制／脚本及 Loki 等外部服务不由该开关停止。预算保护、观测、资源配置编辑和发布保持可用。旧进程现场核验和联合恢复仍属于 T171。

## 状态与操作

固定 DTO 为 `request_id`、`expected_revision`、`action`、`reason`、`confirm`，加两项交接声明。原因 3～500 个 Unicode 字符；未知字段、路径、SQL 和通用域选择器均拒绝。仅真实平台 Root access 用户会话可用，插件、STS、服务及 API Key 不可用。

| 操作 | 结果 | 额外条件 |
| --- | --- | --- |
| `pause` | `paused`，数据库提交后阻止下一步 | 不要求消费者在线；交接锁定中不可用普通暂停退出交接 |
| `begin_handoff` | `handoff`，立即阻止下一步 | 显式原因、确认、CAS |
| `complete_handoff` | `paused`，保留策略复查要求 | 上一开关版本已发布、消费者可用、已登记自动策略均暂停且发布；两项运维声明为 true |
| `resume` | 请求 `open` | 上一暂停版本已发布、消费者可用；交接后的策略仍需全部暂停；本次恢复发布确认前继续拒绝执行 |

普通暂停后恢复会允许原先启用的受控策略继续运行；页面必须提示。交接完成不会恢复历史启用值：先单独恢复开关，再逐项显式启用资源策略。

交接库存只检查当前安装已登记、固定 DTO 策略的数据库正文和期望／确认版本。预算、目标定义和表监控不要求停用；未知域或正文／审计不一致阻止交接完成。文件来源按来源独立核对，归档同时检查普通启用和远端回收，备份还检查演练标志。资源名称默认展示，技术域标识折叠查看，不返回正文、路径或密钥。

`external_stopped` 与 `admitted_tasks_checked` 是操作者声明，明确标注**不代表系统已经检测旧进程停止或完成任务排空**。未登记旧策略不在库存内，不能由空库存推断已经安全交接。

## 事务、发布与暂停优先级

配置保存沿用同事务 CAS／不可变回执／TaskHistory 登记。所有资源配置写入与受控执行先取得安装级开关共享 advisory lock；开关变更取得其独占锁，再取资源锁，固定为“执行开关 → 资源策略 → 归档目标／主机账本”。不存在开关行时也锁定同一键。执行使用同一事务连接，不在 SQL 事务内等待整个长任务完成。

因此，暂停成功前已进入守卫的有界步骤可先完成；暂停成功后不能再进入下一受控步骤。若锁超时／数据库不可达，接口不声称暂停成功，原 UUID 只读核对。开关发布只写本机快照，不执行备份、传输或删除。

暂停读取期望正文即可阻止执行，不依赖 `applied_revision`。消费者禁用或退出时依然可以保存暂停；正式队列登记仍需可用，Redis 入队异常按原恢复链路处理。恢复执行要求期望、确认、本机快照和不可变审计全部匹配，且消费者未退出；不能凭 `mode=open` 单字段认定可以执行。

`execution-control-binding.json` 记录 scope／单调 revision／digest。暂停成功答复前写入独立主机水位，消费者发布也单调写入；`execution-control-snapshot.json` 是只读发布投影。水位比数据库新、行消失、篡改、缺少证明均拒绝执行，不回退 unmanaged。托管原地恢复现按下节写入独立代次；外部工具把维护根也还原的识别仍未完成；也不承诺在暂停事务提交与水位写入之间崩溃时已有成功答复。数据库提交成功但答复／水位确认失败仍按未知结果处理。

## UI、回执与故障

`/monitor/storage` 顶部始终可见入口，弹层采用执行状态／操作确认／执行器交接／本次回执的纵向任务分区，窄屏为同组选择器。操作原因和 CAS 基准跨分区及 SSE 更新保留；载入新版本需明确操作。状态更新复用工作区 SSE，无周期状态查询。

POST 结果未知时锁住提交和关闭，只 GET 原 UUID；404 不代表原写入失败，不自动重发。回执核对原操作全部字段和版本；`operation_revision` 属于原请求，当前 `configuration` 可能已被后续操作更新，不能冒充原请求的生效证明。主机元数据故障时可返回原回执及 unavailable 当前状态。

接口相对 API 前缀为 `/admin/ops/storage/execution-control`、`/changes` 和 `/requests/:request_id`。绑定默认 `/api/v1`，隔离 HTTP 验收使用 `/custom/v2`。发布变更使用正式 `configuration_changed` → SSE，不新增消费者或私有轮询队列。

## 2026-11-08：托管原地恢复栅栏

同一 Core／同一端口的维护恢复在保护快照完成后、`journal.DatabaseTouched=true` 及数据库替换之前，向**既有维护根**写入独立恢复代次。`storage-recovery-binding.json` 与 `storage-recovery-epoch.json` 不属于业务数据库、运维运行目录或恢复载荷；既有恢复目标重叠检查禁止覆盖维护根。标记失败则不触碰数据库；故障补偿、恢复启动成功都不清除它。

安装记录新增 `storage_protocol`（2026-11-08 为 v2；2026-11-09 先升级为 v3，随后独立请求凭据升级为 `powerx.storage-recovery/v4`，见[独立凭据合同](backup-retention-recovery-ledger.md)与[保留回执联合恢复合同](backup-cleanup-retention.md#2026-11-09-t171恢复代次与正式升级联合验收)）。首次旧安装协议升级可初始化空栅栏；协议一旦登记，缺失、权限不当、软硬链接、损坏或安装身份不符均拒绝重建并阻止执行。Bootstrap 在普通安装要求该接线，未接通时受控执行失效关闭；不另建身份、常驻程序或端口。文件锁为非阻塞共享／独占锁；受控有界步骤及开关写入持有共享锁，恢复提交代次使用独占锁，忙则明确拒绝，不越过当前步骤。

本版本托管恢复保留当前安装的 `storage_governance` 部署接线，包括主机／文件系统身份、运行目录和开关，不允许旧 YAML 关闭或重定向守卫。当前安装身份、连接、端口与快照／维护位置仍沿既有恢复合同保留。快照 Core 缺少新协议时走已有 dev 本地适配流程，保留当前 Core，明确不是历史程序逐字节恢复证明；不能因此放宽已有现代包的能力目录完整性检查。

配置状态新增 `recovery`。独立代次与执行文档 `recovery_epoch` 不匹配、或新确认尚未发布时，即使旧数据库和旧运行投影完全匹配且历史开关为 open，仍阻止下一受控步骤。Root 先通过 `prepare_restore` 提交当前 `expected_recovery_epoch`、CAS、UUID、原因和三项声明，原子重建本安装所有已接管配置并暂停执行策略；正式 TaskBus 发布后逐资源核对，再通过独立 `acknowledge_restore` 确认。系统检查来源、审计、发布内容、预算、目标验证与凭据代次，以及已登记自动策略均暂停。旧执行器停用、已接纳任务核对及部署环境现场核对仍是运维声明，不是外部进程自动检测或真实取回证明。

确认仅保存 `paused` 与新代次，并保留 `review_policies=true`；本次发布确认后才能单独恢复开关，再逐项启用资源策略。旧确认回执保持原代次，不能解除后续恢复；SSE 不覆盖表单冻结的代次，新代次冲突必须明确载入最新状态并重新声明。响应未知仍只 GET 原 UUID，404 不授权重发。UI 新增“恢复后核对”分区，待核对状态和入口在顶部持续可见。

本轮原生测试实际重放旧控制配置／版本行和配套运行文档，证明独立新代次仍阻止执行；这不是整库 pg_restore、完整整站恢复或生产验收。早期切片中 DB-only 回滚只阻止执行；下方 2026-11-08 统一重建已补齐受控路径的版本重建及 S3 凭据／目标代次核对。外部恢复工具／整盘回退及真实旧进程交接仍待验收。详细证据见 [本轮验收](evidence/storage-recovery-control-validation-20261108.json)。

## 未验收范围

本地独立 PostgreSQL／HTTP／TaskBus／Nuxt 验收不代表日常部署或生产生效。本轮未迁移日常库、未改策略、未重启用户服务、未改正式站或 Mac 用户归档对象。受支持资源的跨版本恢复重建已进入隔离验收；日常实例部署和完整物理恢复、旧进程现场证明、外部回退、自动恢复演练、外部 KMS、SSH 凭据恢复路径、长期外部目标、双环境及 7／14 天运行证据继续待办。


## 2026-11-08 统一重建与逐资源核对

`prepare_restore` 仅允许平台 Root，在独立恢复代次未确认时调用。执行开关独占锁、资源 CAS、不可变审计与正式 TaskBus 注册位于同一 PostgreSQL 事务；任何来源、归属、审计或任务注册失败均回滚。数据库版本、历史审计、运行目录及单项策略水位共同决定新版本下限，允许恢复操作跨版本递增，普通保存仍只加一。存在本机接管水位但数据库缺失对应资源时拒绝重建，不能回退 legacy。

涵盖表监控、主机预算、调用日志期限、两类系统表期限、逐来源文件生命周期、归档目标／策略、数据库备份与整站快照。每份重建文档保存独立代次、Root 请求、原配置版本／摘要及环境摘要；后续正常编辑延续来源证明。备份数据库行与配置同事务更新；清理、归档、远端清理、备份／恢复演练、快照启用／当前策略均清零。监控保持设置；共享预算取恢复配置与当前投影的更严格限制。同盘的安装文档按完整 scope 隔离，共享预算和租约继续共用，不能因启动顺序覆盖其他实例绑定。

`recovery.resources` 返回每个资源的 `pending/ready` 与明确原因。确认要求各资源的数据库、不可变版本和实际投影一致；旧启用且尚未接管的资源也进入待办。`prepared=true` 只证明本代次已经重建，不代表全部发布、目标验证或现场交接完成。确认后继续暂停；恢复全局开关和逐项启用保持分开。页面通过现有 SSE 变更刷新，无周期性状态查询；新恢复代次允许显示回滚后的较低数据库版本，原表单与未知请求仍绑定旧 UUID／代次。

恢复协议 v1 自动升级到 v2 时只改完整证明的协议字段，保留安装、锚点、代次、恢复任务及时间。绑定先落盘，升级中断可以续接；丢失证明不重建。旧程序无法读取 v2，托管恢复不得执行不理解统一重建的旧 Core。

### 操作与故障处理

1. 由服务所有者部署新构建并按原方式启动；本改动不替用户重启日常服务。无新增数据库表或常驻端口，沿用既有治理迁移、维护根和 TaskBus。
2. 托管恢复后进入“恢复后核对”，核实旧执行器、已接纳任务及当前环境，再提交“重建恢复配置”。等待 SSE 显示每项发布结果。来源变化先修复当前部署；缺少配置／审计则恢复相匹配的权威数据，不删除水位绕过。
3. S3 凭据显示“恢复后待核对”时重新输入并保存，禁止接管旧明文代替确认；旧吊销仍拒绝使用。逐个重新验证归档目标，完整验证通过后再确认恢复。SSH 尚无对应凭据代次合同，继续阻止；须迁移到受控 S3 路径或补齐合同，不自动放行。
4. TaskBus 发布中断使用既有任务恢复机制；提交响应未知只查原请求。不要重复重建来消除未知状态。确认恢复后仍暂停，按资源核对期限、容量、归档开关后另行启用。
5. 回退须保留 v2 恢复保护与独立维护根。不能通过降级为 v1、清空 epoch、删除绑定／版本或覆盖凭据来恢复执行；不支持 v2 的旧构建不属于可用回退版本。外部整盘回退必须另行证明维护根未一起回退。

证据见 [统一恢复验收](evidence/storage-recovery-reconciliation-validation-20261108.json)。这些检查没有宣称实际归档数据取回、备份业务恢复或生产接管已经完成。
