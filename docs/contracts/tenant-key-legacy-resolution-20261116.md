# 租户历史重复密钥标识兼容修复

## 已确认的问题

2026-11-16 对 `agent-dev.starrtoylumi.com` 的只读诊断确认：Qwen 凭据更新于 00:23:51，两条同租户、同环境、同 KID 的密钥记录同时存在。ID 1 已停用，其私钥无法被当前服务主密钥解包；ID 2 启用，使用当前配置能解包，并成功解开目标凭据。诊断只输出解密结果和 Key 是否存在，没有输出凭据、私钥或主密钥。

旧读取按 scope + KID 执行 `First()`，优先取 ID 1，导致模型平台请求前就失败。Loki 历史日志同样记录 `unseal api_key failed` / `cipher: message authentication failed`。动态在线模型列表无法绕过凭据解密。

## 修复边界

- 仓储返回严格限定租户、环境、KID 的所有未删除候选，包含停用的历史密钥。
- 服务依次解包并验证目标 RSA 密文，只有确实解开目标凭据才使用；不能仅凭 active 或私钥解包成功判断。
- 全部候选失败时返回明确的凭据解密错误，不泄露密钥材料；不会选择其他租户或环境的记录，不修改数据库。
- 新建和轮换在已有 scope 锁内扫描全部历史 KID（包括软删除），递增最大版本，防止无激活记录时重新从 v1 开始。PostgreSQL 使用事务 advisory lock，SQLite 使用进程锁。
- 本次不删除或重命名历史记录，不更换 server.secret_key，不自动轮换密钥，不执行数据库迁移。现有重复记录尚不允许直接添加唯一约束；本次通过正式服务入口的锁和版本分配防止再次复用，尚未提供数据库唯一约束来防御绕过服务的直接写入。
- 这是共享 tenantkeys 修复，适用于调用该服务的全部 Provider 和其他凭据消费者；不代表各平台真实 API 均已验收。

## 部署与运行验收

本修复当前仅为本地源码及隔离测试，不代表远程服务已修复。按现有发布流程构建并部署 Core 后端；不需要改 Provider 配置或重填 Key。日常服务由用户执行重启，Agent 不自行停止或重启。

重启后首先用现有 Qwen 凭据读取在线模型，再保存、刷新确认恢复。验收要求：无解密错误，模型读取成功，保存成功且刷新后模型和参数保持。随后按实际已配置的其他 Provider 验证同一流程。若上游返回鉴权、协议或网络错误，应作为独立问题处理，不能将本次解密修复当成上游验收。
