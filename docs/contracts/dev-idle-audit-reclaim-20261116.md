# dev 空轮询审计回收（2026-11-16）

## 授权和固定范围

用户明确将 **dev** 的“成功且未取到消息”审计改为保留最近 24 小时，其他记录先归档再清理；prod 的原七天临时维护规则不变。

本次只处理 `powerx_dev.public.capability_registry_invocation_traces` 和它唯一引用的 `capability_registry_event_publications`。要求已登记租户、Core 平台能力、AI Craft 调用身份、`taskqueue.v2/dequeue`、相同租户、成功、无 fallback／错误、响应明确为零条消息，以及通知负载完整匹配。最近 24 小时、失败、真实消息、未知来源、额外引用及已投递通知均保留。

部分旧通知有一次发布尝试和 UUID 确认号，但终态为 `unrouted`。根据正式 `PublishAcknowledged` 合同，该状态表示发布时订阅者数量为零，UUID 不是业务送达证明。dev 专项仅接受已分类通知、一次尝试、合法 UUID、发布时间等于终态时间且无错误；重试、未知确认号、已投递和未知终态不放宽。默认七天规则完全不变。

## 维护执行器

`idle_taskqueue` 新增显式 `-dev-keep-hours 24` 和必填 `-expected-dev-commit`，只能绑定 `powerx_dev`。每批检查开发站构建指纹；Core 升级后停止，不自动沿用授权。普通七天任务保持原参数、二进制与批量上限；dev 专项单批最多 5000 对。

每个事务先锁定并复核来源、引用和结构；以 PostgreSQL binary COPY 保存原始行，压缩并记录 SHA256，再恢复到临时表逐行比较。核验通过后才删除并写提交回执。未知提交、缺失回执和归档不一致时停止，不自动重试。

回收副本转存到操作机私有恢复目录时，必须逐文件匹配提交回执中的 SHA256，写入 custody 记录后才回收服务器重复副本。归档不自动删除。清理仍执行八 GiB／主机保护线，不通过缩小安全预留启动操作。

现有临时维护器支持 dev 独立的 24 小时、冻结 ID 上界及运行版本绑定，状态使用 `dev-24h.json`；prod 参数保持七天。此机制仅处理已核准的历史噪声范围，不代替 Core 的常规保留策略，也不扩大到新增记录。

定时 dev 维护必须绑定安装的 `scope_id`，在删除事务中复用 Core 执行配置的共享 advisory 锁；一旦该域出现正式 `execution-control` 配置，即停止临时删除并交回 Core 核对。正式紧急暂停或接管不能被临时脚本绕过。原手动 DBA 回收和周期维护使用不同二进制路径，避免执行中替换程序。
